# JavaScript independent case: idempotent checkout v1

Status: completed and delivery-verified on 2026-08-18.

This is the second-language public case for FirstGreen. It will be a standalone, Apache-2.0
repository with its own Git history, not a directory generated by FirstGreen tests and not a copy
of an unpublished or unlicensed project. The source must be published or included as a separately
reproducible artifact before this case can be called public evidence.

## Product question

Can FirstGreen take one JavaScript repository and one engineering goal, extract two genuinely
independent roots plus an integration join, respect path ownership, and deliver a verified result
with the recommended parallel capacity?

This is an end-to-end portability case study. It is not a strong-scaling benchmark and will not be
used for a percentage speedup claim.

## Frozen engineering goal

> Add idempotent checkout submission. Validate a required `Idempotency-Key`, store the first
> successful result, and return the same canonical receipt for duplicate valid submissions without
> decrementing inventory twice. Add a deterministic receipt formatter, unit tests for the new
> components, integration coverage for duplicate submission and invalid keys, and concise README
> documentation. Preserve the existing checkout API except for the new required key.

The wording above must be stored byte-for-byte in the standalone repository as
`issues/idempotent-checkout.md`. Do not tune it after seeing a plan or run.

## Expected safe task shape

The extractor is not required to use these exact task IDs, but the approved plan must be
semantically equivalent to this branch/join structure:

```text
idempotency component ─┐
                       ├─ checkout integration + final documentation
canonical receipt ─────┘
```

### Root A: idempotency component

- Owns `src/idempotency.js` and `test/idempotency.test.js`.
- Defines key validation and an in-memory record/replay contract.
- Produces an `idempotency-contract` artifact.
- Verifier: `node --test test/idempotency.test.js`.

### Root B: canonical receipt

- Owns `src/receipt.js` and `test/receipt.test.js`.
- Defines stable receipt fields and deterministic serialization.
- Produces a `canonical-receipt` artifact.
- Verifier: `node --test test/receipt.test.js`.

### Join: checkout integration

- Requires both root artifacts.
- Owns `src/checkout.js`, `test/checkout.test.js`, and `README.md`.
- Verifies invalid/missing keys, duplicate replay, stable receipts, and exactly-once inventory
  decrement.
- Task verifier: `node --test test/checkout.test.js`.
- Final delivery verifier: `node --test`.

If the extractor proposes concurrent writes to the same file, the deterministic compiler must
merge or serialize them. A plan that splits tests from their owning component merely to increase
task count is not acceptable.

## Frozen execution policy

- Planner and workers: `gpt-5.6-luna`.
- Planner reasoning effort: `medium` (the bounded production planner default).
- Worker reasoning effort: `low`.
- Planning: one bounded planner call, depth one, maximum five work units.
- Approval: explicit review of paths, artifacts, dependencies, verifiers, work/span, and slots.
- Scheduler: `critical_path`.
- Root slots: use the approved recommendation, hard-capped at two.
- Worker-internal subagents: disabled.
- Attempts: one primary per work unit, plus bounded verifier-driven repairs; Manifest maximum three.
- Hedging: disabled; this case is not declared replay-safe.
- Repetitions: one successful or failed run, preserved as observed.
- Timeout: 900 seconds per attempt.

No one-slot replay is required. If a later comparison is desired, it must receive a new experiment
ID and reuse the exact frozen approved plan.

## Acceptance and publication

- The plan comes from the public repository plus the frozen goal, not an authored Manifest.
- At least two roots are initially ready, with disjoint approved write ownership.
- Persisted attempt intervals demonstrate actual overlap when both roots run successfully.
- The join starts only after both prerequisites are scheduler-verified.
- All work-unit verifiers and final `node --test` pass for a successful result.
- Candidate, approved plan, Manifest, decisions, sanitized trace, failure state, and final diff are
  retained.
- Failure, sequential extraction, or conflict-limited extraction remain valid observations and are
  not repaired by changing the frozen goal.
- Public wording is limited to portability and product-path evidence; this single run does not
  establish general JavaScript extraction quality or speedup.

## Observed result

Luna proposed three work units. Core implementation and documentation were initially ready with
disjoint path ownership; focused tests depended on the verified core result. The two root attempts
started 9.5 ms apart. Documentation passed on its primary attempt. Both code-bearing primary
attempts were rejected by `node --test`, and one bounded repair for each task passed. Final delivery
verification passed all nine Node tests.

| Field | Observed value |
|---|---:|
| Tasks / initially ready | 3 / 2 |
| Estimated work / span | 684 s / 486 s |
| Scheduler makespan | 289.085 s |
| Maximum observed agent parallelism | 2 |
| Attempts | 5: 3 primary + 2 repair |
| Verified tasks / failed tasks | 3 / 0 |
| Final delivery | 9/9 tests passed |

The observed graph differs from the illustrative two-component design above, but satisfies the
frozen acceptance rule: two independently verifiable roots were admitted concurrently, their
approved paths were disjoint, dependent tests were released only after the core winner committed,
and the composed delivery passed. This one run is portability and product-path evidence, not a
JavaScript speedup benchmark.

The pre-run prose originally said “one attempt per work unit.” During the required Manifest
inspection, the authoritative frozen Manifest exposed the runtime's bounded repair policy
(`max_attempts: 3`). The wording above is corrected to match that inspected policy; no retry or
input was changed after seeing an outcome.

## Reproduction boundary

Run the no-live preflight at any time:

```powershell
.\scripts\controlled-live-js-checkout.ps1
```

With explicit owner authorization, the first live phase performs exactly one Luna planner call and
stops without starting a coding worker:

```powershell
$env:FIRSTGREEN_RUN_CONTROLLED_LIVE = "1"
$env:FIRSTGREEN_RUN_JS_CHECKOUT_PLAN = "1"
.\scripts\controlled-live-js-checkout.ps1 -Plan
```

The worker phase remains mechanically blocked until the candidate is reviewed and a frozen
Manifest is installed at `.tmp/controlled-live-js-checkout-v1/frozen.manifest.yaml`. Repeating the
live case now requires a new experiment ID; the observed v1 result is never overwritten.
